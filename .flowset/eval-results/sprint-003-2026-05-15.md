## Sprint Retrospective

### 잘된 점

1. **단일일 4 마일스톤 완주**: 2~3주 예정이던 Sprint를 단일일에 M1~M3 코드 + M4 PRD 패치까지 마쳤다. 마일스톤별 evaluator 게이트가 각 단계의 머지 적격성을 객관 검증해 다음 단계 진입 신뢰도가 높았다.

2. **테스트 증분 +64%**: Sprint 002 70 → Sprint 003 115. AC-5 임계 90을 25개 초과. Sprint 002 evaluator가 지적했던 "LRU trim 직접 측정 부재"를 단위 테스트 3개로 정확 해소 + lastAccessedAt 시간차 검증까지 직접 구현.

3. **enum + boolean 구조화로 깨지기 쉬운 문자열 매칭 제거**: M1에서 `result.reason.includes('전역 동의' | '비밀번호' | '결제')` 같은 한국어 매칭이 `result.pageWideBlock` boolean으로 일괄 전환. 번역/언어 변경에 무관해졌고 card_pattern 같은 기존 누락 분기도 자동 포괄.

4. **DomainPolicyStore가 DomainFilter를 wrap하는 깔끔한 분리**: Store는 영속/정책 관리, Filter는 평가 — IPC 6개 모두 Store 경유, Filter 직접 호출 없음. 평가 경로 불변이라 G-004 회귀 위험 최소화.

5. **자동 검증 4종 일관 통과**: M1~M3 각 단계에서 lint / typecheck / test / build 모두 PASS 유지. 회귀 깨짐 0건.

6. **PRD-코드 동시 진화**: M4에서 PRD v0.3.1을 별도 후속 작업으로 미루지 않고 같은 날 패치. requirements.md / state.md / change_history.md / 04_requirements.md / 06_data_model.md / 11_dev_tasks_and_ops.md / README.md 7개 SSOT 파일 일관 갱신.

### 어려운 점

1. **IPC 이벤트 채널 통합 vs 분리 결정**: 계약 §3 AC-3가 명시한 5종 채널 (start/progress/done/error/aborted)을 코드에서는 3종 + stoppedReason 필드로 통합 채택. M2 evaluator D에서 Partial로 분류. 의미적 동등성은 확보됐으나 계약 문구와 코드의 미세 어긋남 발생.
   - **개선**: 다음 Sprint 계약 작성 시 "채널 구조의 단일성 vs 의미 단일성 중 어느 쪽을 우선하는가"를 명시. 또는 계약 갱신 PR로 현재 통합 형태를 정정 반영.

2. **사용자 사전 설계 입력의 evaluator 처리**: M2 D는 사용자가 사전에 통합 채택을 명시했음에도 계약 문구와 다르다는 이유로 Partial로 분류됐다. evaluator가 "사용자 사전 결정 vs 계약 문구" 충돌을 어떻게 다룰지 명시 필요.
   - **개선**: contracts/sprint-NNN.md에 "사용자 사전 결정으로 계약 문구 변경이 동반된 항목" 섹션 신설.

3. **PageNodeExtractor 인라인 합본의 의미 단위**: `<p>foo <strong>bar <em>baz</em></strong></p>` 같은 중첩 인라인을 `innerText`로 합본 처리한 첫 구현이 의미 단위로 적정한가? — 단위 테스트는 통과하나 실제 페이지에서 긴 합본 텍스트가 청크 4000자를 넘기는 케이스의 UX 영향은 수동 QA 필요.
   - **개선**: Sprint 004에서 실측 페이지 (위키피디아 / 뉴스 사이트) 대상 PageNodeExtractor 수동 QA 추가.

4. **단일일 진행 vs 분산 검증**: 단일일 4 마일스톤 완주는 속도 측면 우수하나 실제 사용자 QA / 수동 회귀가 단위 테스트로만 검증된 영역(파일 다운로드 다이얼로그, JSON 선택, confirm 동작 등)에 대한 검증 공백을 남겼다.
   - **개선**: Sprint 003 종료 핸드오프에 수동 QA 체크리스트 추가 권고 (M3 evaluator 후속 4 항목).

### 학습

1. **계약 명시도가 evaluator 안정성을 결정한다**: AC-1 ~ AC-7의 임계가 정량적일수록 (예: "≥ 10 tests", "≤ 절반") evaluator가 객관 채점 가능. 정성 임계는 Partial 발생 빈도가 높다. → 다음 Sprint 계약은 모든 임계를 정량화하거나 binary 조건으로 표현.

2. **enum/boolean 우선 설계가 한국어 코드의 안정성 핵심**: 문자열 매칭 (`reason.includes('전역 동의')`) 같은 패턴은 i18n / 메시지 변경 / 한국어-영어 혼용 시점에 깨지기 쉽다. M1에서 이를 enum 비교로 전환한 결정이 향후 자막/TTS 기능 추가 시 회귀 위험을 큰 폭으로 감소시킬 전망.

3. **wrap 패턴(Store → Filter)이 SSOT 단순화에 효과적**: Store가 Filter를 wrap하고 모든 외부 호출을 Store로 단일화한 구조 덕에 "영속과 평가의 단일 진실 경로"가 명확. 향후 Subtitle / TTS 모듈에도 같은 패턴 적용 가능.

4. **PRD 패치를 Sprint 종료 시점에 일괄 처리**: PRD를 M1/M2/M3 각각 분산 갱신하지 않고 M4 단일 PR로 일괄 처리한 방식이 SSOT 일관성 보장에 효과적. 단, M1 결정 → M4 반영까지 컨텍스트 손실 위험 → 마일스톤별 evaluator 보고서에 "PRD 패치 항목" 누적 기록 필수.

5. **테스트가 evaluator 신뢰도의 60% 이상**: 본 Sprint에서 evaluator가 Pass 판정을 내릴 때 단위 테스트 + 자동 검증 통과가 결정적 근거였다. 단위 테스트 없는 영역(IPC, UI 다이얼로그)은 evaluator가 코드 인스펙션만으로 채점 → Partial 가능성 상승.
