## 항목별 채점

### AC-2-1 closeOthers API
- 임계: `TabManager.closeOthers(keepId)` — keepId 외 모든 탭 close, keepId 활성 보장, 빈 탭 자동 open 시나리오 발동 안 함 (keepId 존재 보장)
- 결과: `TabManager.ts:133~151` `{ ok: boolean; closed: string[] }` 반환, keepId 미존재 시 ok=false + 변동 없음, keepId가 활성 아니었으면 활성 전환 + lastActiveAt 갱신, closed.length>0일 때만 emit. main/index.ts handler가 `!result.ok` 시 false 반환 + 정상 시 setActiveTabView(keepId) 호출.
- 판정: **Pass**
- 근거: 계약 동작 모두 일치. closeOthers는 keepId 1개를 살리므로 size>=1 보장 → 빈 탭 자동 open 회피 (계약 7번째 리스크 항목 부합).

### AC-2-2 closeRight API
- 임계: `TabManager.closeRight(fromId)` — fromId 오른쪽(order index >) 탭들만 close, fromId 활성 유지
- 결과: `TabManager.ts:157~175` order.slice(fromIdx+1)로 정확한 오른쪽만 추출, fromIdx<0이면 ok=false, toClose 비어있으면 ok=true closed=[]로 no-op. 활성 탭이 닫히는 집합에 포함됐을 때만 fromId로 전환 (이미 왼쪽 활성이면 보존). main handler에서 destroy + setActiveTabView(active).
- 판정: **Pass**
- 근거: "fromId 활성 유지"를 "닫힌 집합에 활성이 있었을 때만 fromId로 전환"으로 정확히 구현. 활성 보존 시멘틱이 계약과 일치.

## 강점

1. **Helper API 설계** — closeOthers / closeRight가 `{ ok, closed: string[] }` 패턴으로 main/index.ts 측에서 destroyTabView 순회 + setActiveTabView 후처리를 일관되게 수행 가능. close 메서드와 시멘틱 분리 (single tab close vs bulk).
2. **활성 보존 시멘틱 정밀** — closeRight에서 "활성이 닫힌 집합 안에 있었을 때만 fromId 전환"이라는 미세 동작을 별도 테스트로 검증.
3. **OS 네이티브 popup 채택** — 계약 §7 리스크 2번 권고 그대로 적용. renderer 자체 메뉴 회피 → 접근성/룩 일관성.
4. **disabled 분기 단위 분리** — onlyOne / isRightmost를 const로 추출해 가독성 + 추후 다른 항목 추가 시 확장성.
