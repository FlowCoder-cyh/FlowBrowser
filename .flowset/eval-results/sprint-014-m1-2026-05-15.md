## 항목별 채점

### A. AC-1 DeviceCodeFlow 코어 구현
- 임계: requestUserCode / pollOnce / exchangeTokens / refreshTokens 구현 + Codex CLI 응답 매트릭스 정합 + fetch 의존성 주입
- 결과:
  - `requestUserCode()` → `POST {issuer}/api/accounts/deviceauth/usercode` body `{ client_id }`, 응답에서 `device_auth_id` + `user_code | usercode` (alias) + `interval` (number 또는 문자열) 파싱. `verification_url`은 `{issuer}/codex/device`로 조립
  - `pollOnce(deviceAuthId, userCode)` → `POST {issuer}/api/accounts/deviceauth/token`. 200 시 authorization_code + code_challenge + code_verifier 반환, 403/404 → pending, fetch throw → error, 그 외 status → error
  - `exchangeTokens({ authorizationCode, codeVerifier })` → `POST {issuer}/oauth/token` form-urlencoded body `grant_type=authorization_code` + `code` + `code_verifier` + `redirect_uri={issuer}/deviceauth/callback`
  - `refreshTokens(refreshToken)` → 동일 endpoint form-urlencoded `grant_type=refresh_token`. refresh_token 회전 반환 시 갱신, 미반환 시 기존 유지 (sprint-014 §7 리스크 #4 명시 처리)
  - `bundleFromResponse()` 헬퍼 — `issuedAt = Date.now()`, `expiresAt = issuedAt + expires_in*1000`, `expires_in` 미반환 시 3600s fallback
  - `DeviceCodeFlowOptions.fetchImpl` 주입 → 단위 테스트에서 fetch 모킹 가능
  - issuer trailing slash 정규화 (`.replace(/\/$/, '')`)
- 판정: **Pass**
- 근거: 사용자 메시지의 특이사항대로 Codex CLI `codex-rs/login/src/device_code_auth.rs` + `server.rs`를 gh api로 직접 읽어 endpoint 정확도 확보. DEFAULT_ISSUER=`https://auth.openai.com`, DEFAULT_CLIENT_ID=`app_EMoamEEZ73f0CkXaXp7hrann`는 Spike 1 §2 "Public Client ID"와 정확히 일치. PKCE를 서버가 발급하는 흐름은 RFC 8628 표준이 아니라 Codex 자체 변형으로, 본 평가에서는 "Codex CLI 소스 정확성 검증 후 갱신"이라는 사용자 메시지 단서와 일치하므로 인정한다.
