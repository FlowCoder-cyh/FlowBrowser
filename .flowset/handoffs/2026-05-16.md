## 2. 실측 후 도출된 본질적 한계

### Phase 1 (실시간 페이지 번역) — 효용 약함

**기술 한계**:
1. **속도**: gpt-5.5 reasoning low로도 49 문단 처리에 수십 초~분. Wikipedia (2393 문단)는 사실상 사용 불가
2. **ChatGPT 구독 한도**: 5h/주. 페이지 1개당 49+ 호출이면 며칠 안 소진
3. **Codex 백엔드는 코딩 어시스턴트 전용**: 번역 use case는 회색지대 우회 호출. 품질 우위 보장 안 됨
4. **ToS 회색지대**: Anthropic 2026-04 같은 패턴 차단 전례. OpenAI 언제든 차단 가능

**효용 한계 (Chrome 내장 번역 대비)**:
- Chrome 번역: 빠름, 무료, 설정 0, 품질 보통
- 우리 앱 Phase 1: 느림, 비용/한도, OAuth 설정, 품질 ?
- **단순 페이지 번역만이면 차별점 사실상 없음**

**핵심 통찰**:
> OpenAI는 ChatGPT 구독을 자연어 일반 use case (번역/요약)에 호출하는 공식 경로를 제공 안 함. Codex OAuth는 사실상 "코딩 어시스턴트 전용"의 인증 토큰. 우리가 콘텐츠 번역으로 사용하는 건 본질적 fit 안 맞음.

### Chrome 확장과 비교

**Chrome 확장 (Sider / MaxAI / Glasp / Monica 등)**:
- 사이드패널 + 페이지 Q&A
- 텍스트 선택 → AI 분석
- 다중 탭 chrome.tabs API
- 노트/하이라이트
→ 자체 브라우저 정당화 어려움

확장이 못 하는 것:
1. **OS 파일시스템 직접 + 대용량 로컬 인덱스** (IndexedDB 용량 제약 회피)
2. **백그라운드 영구 작업** (service worker 제약 회피)

5. **시스템 통합** (트레이/단축키/클립보드/다른 앱 IPC)

### 신규 방향: **AI 콘텐츠 메모리 + 워크스페이스 브라우저**

**한 줄 정의**:
> 본 페이지를 자동 기억하면서, 프로젝트별로 환경이 격리되는 AI 리서치 브라우저

**핵심 가치 제안**:
1. **본 페이지 자동 인덱싱** — 사용자가 본 모든 페이지 로컬 DB + 임베딩 누적
2. **워크스페이스 격리** — 프로젝트별 탭/메모리/AI 컨텍스트/노트 분리
3. **시간축 + 의미 검색** — "3개월 전 본 그 글", "AI 관련 본 글 모아줘"
4. **AI 횡단 분석** — 워크스페이스 메모리 retrieval로 비교/요약/Q&A

**Chrome 확장 대비 차별 (재활용 못 하는 영역)**:
- 다중 워크스페이스 격리 (단일 환경 회피)
- 수만 페이지 임베딩 인덱스 (SQLite + sqlite-vec, IndexedDB 용량 회피)
- 시스템 통합 (클립보드/단축키/트레이)
- 백그라운드 영구 인덱싱/번역

**호출 효율**:
- 인덱싱은 로컬 (LLM 호출 X 또는 text-embedding-3-small 미세 비용)
- AI 검색/Q&A는 질의당 1~3회 (Phase 1 49+회 vs)
- ChatGPT 구독 한도 충분 (가벼운 호출)

### 번역의 재정의 — 백그라운드 장시간 처리

**기존 폐기**: 실시간 페이지 텍스트 교체 (replace/overlay)

**신규 유지**: 사용자가 "이 PDF/논문 번역해줘" 요청 → 백그라운드 처리 + 완료 시 알림

**시나리오**:
- 사용자가 25페이지 학술 논문 페이지 → 우클릭 "백그라운드 번역" 또는 "AI 메모리에 한국어로"
- 시스템 트레이/알림으로 "진행 중" → 완료 시 "📚 논문 번역 완료" 알림 + 클릭으로 보기
- 그동안 사용자는 다른 작업
- 결과는 **워크스페이스 메모리 + 별도 한국어 뷰**로 저장 (재방문/검색 가능)

**왜 백그라운드가 fit**:
- 시간 제약 없음 = ChatGPT 구독 한도 천천히 사용
- gpt-5.5 reasoning medium/high도 가능 (품질 우선)
- 사용자 인지 시간 0 (UI 대기 없음)
- 결과 영구 저장 = 같은 논문 두 번 안 번역
