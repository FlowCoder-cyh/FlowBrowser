## 1. 배경 — T17 라인 종결

write-path wiring(#262)으로 query/write 양쪽이 provider-aware 가 됐다. T17e 는 그 end-to-end 가치를 통합 테스트로 증명 — v06 schema(vec_pages_1024/768)에서 워크스페이스별 embedding_model 격리가 write path(인덱싱 적재) + query path(검색) 양쪽에서 성립함. scope/단언은 codex 019e6ea0 협의(write-path 와 동일 thread).

## 2. codex scope 협의 (019e6ea0)

- **Q1 write path** = processNextEmbeddingJob 직접 반복 drain (worker scheduler 안 씀 — 이미 단위 테스트, 통합은 결정적·간결). buildEmbeddingClientForModel(ws.embedding_model, getProvider) 로 resolveEmbeddingClient.
- **Q2 query path** = handleSearchQuery (프로덕션 경로 — embedding_model 해소 + provider 선택 + EmbeddingClient dim 주입까지 E2E). SearchService 직접 호출은 부족.
- **Q3 단언 보강**: countPages 는 dim 합산이라 cross-dim 부적합 → searchPages per-dim. provider spy 는 dimensions+modelHint 까지. handleSearchQuery 결과 type/pageId/url/title. dimension mismatch → 'failed'(provider_unavailable 아님)+vector 0.
- **Q4** 신규 파일 (m4-pipeline 은 v05 applySchema 기반). scope = page only (vec_notes 분리는 VectorIndex unit 커버).
